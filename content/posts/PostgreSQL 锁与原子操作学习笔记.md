# PostgreSQL 锁与原子操作学习笔记

这份笔记从并发访问共享数据开始，介绍 PostgreSQL 中常见的锁，以及理解自旋锁需要的原子操作、CPU 缓存和 ARM64 基础。可以在每节末尾补充自己的例子和实验结果。

## 1. 为什么需要锁？

多个执行者同时访问同一份数据时，如果缺少协调，就可能出现结果错误。

例如两个任务同时给计数器加一：

```text
初始 count = 0

任务 A 读取到 0        任务 B 读取到 0
任务 A 计算出 1        任务 B 计算出 1
任务 A 写回 1          任务 B 写回 1

最终 count = 1，实际执行了两次加一
```

这叫作**丢失更新**。虽然 `count++` 在 C 代码里只有一行，但它不一定作为一个不可分割的操作执行。

一种解决办法是加锁：

```text
获取锁
更新共享数据
释放锁
```

同一时刻，只有拿到锁的执行者可以进入受保护的区域。这段区域叫作**临界区**。

几个相关概念：

- **并发**：多个任务的执行时间有重叠。
- **共享数据**：多个执行者都可以访问的数据。
- **锁竞争**：多个执行者同时想获取不兼容的锁，部分执行者需要等待。
- **死锁**：多个执行者相互等待对方持有的资源，形成等待环。

普通读写本身不会导致死锁。没有正确同步的并发访问可能产生数据竞争或错误结果；死锁则是另一类问题。

## 2. PostgreSQL 中有哪些锁？

PostgreSQL 的锁服务于不同层次的问题，不能把它们当成同一种东西。

| 机制 | 主要作用 | 初步理解 |
| --- | --- | --- |
| 表级锁等常规锁 | 协调事务或会话对数据库对象的访问 | 有不同锁模式，冲突时可能等待 |
| 行级锁 | 协调针对同一行的修改或显式锁定 | 冲突时可能等待其他事务结束 |
| LWLock，轻量级锁 | 保护数据库内部的共享数据结构 | 有共享和排他模式，等待者可以睡眠 |
| Spinlock，自旋锁 | 保护非常短的共享内存临界区 | 获取失败时先循环重试，之后可能退避或睡眠 |
| Advisory lock，咨询锁 | 协调应用自己定义的逻辑资源 | 应用主动申请；可按事务或会话持有 |
| MVCC | 决定事务能看到哪些数据版本 | 它不是锁，但与锁共同处理并发 |

一个数据库操作可能先后使用多种机制。锁的具体模式、释放时机和等待行为要结合操作判断。

## 3. MVCC、表锁和行锁

### 3.1 MVCC 与锁的关系

MVCC 是多版本并发控制。可以先把它理解为：数据库保存并判断数据的不同版本，让事务按快照规则看到合适的数据。

普通查询通常不需要通过给每一行加排他锁来读取，但这不代表查询完全不使用锁：它仍可能获取表级锁，也会使用数据库内部的同步机制。

MVCC 和锁共同工作。例如，多个事务都能读取某一行的可见版本，但并发修改同一行时，仍可能发生等待或冲突。

待补充：不同隔离级别下，普通 `SELECT`、`UPDATE` 和 `SELECT ... FOR UPDATE` 的行为。

### 3.2 表级锁

不同 SQL 会申请不同模式的表级锁。一些模式可以共存，一些模式互相冲突。是否会阻塞，需要看具体的锁模式，不能只凭 SQL 是“读”还是“写”判断。

待补充：常见 SQL 申请的表锁模式与冲突关系。

### 3.3 行级锁

`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等操作可能对同一行产生修改或锁定冲突。等待其他事务时，观察到的等待信息可能与事务 ID 有关。

行锁状态不能简单理解为“每一行都必然在 `pg_locks` 中长期显示一条记录”。

### 3.4 两个会话的小实验

在测试数据库中准备数据：

```sql
CREATE TABLE lock_demo (id integer PRIMARY KEY, value integer);
INSERT INTO lock_demo VALUES (1, 0);
```

会话 A：

```sql
BEGIN;
UPDATE lock_demo SET value = value + 1 WHERE id = 1;
-- 暂时不提交
```

会话 B：

```sql
BEGIN;
UPDATE lock_demo SET value = value + 1 WHERE id = 1;
-- 观察它是否等待
```

随后提交会话 A，观察会话 B；实验结束时提交或回滚两个事务，并清理测试表。

待补充：会话 A 提交和回滚时，会话 B 的结果分别是什么？

## 4. 自旋锁是什么？

自旋锁是一种等待锁的方式：**拿不到锁时，先不立即睡眠，而是反复检查或尝试获取。**

```text
尝试获取锁
    ├─ 成功：操作共享数据，然后释放锁
    └─ 失败：等待片刻，再次尝试
```

自旋适合锁很快就可能释放的场景，因为线程或进程进入睡眠并被唤醒也有成本。但自旋期间仍会消耗 CPU；如果等待时间长，或者很多核心同时竞争一把锁，成本可能明显增加。

实际实现可能在自旋多次后选择短暂睡眠，而不是无限循环。因此，自旋锁一般用来保护非常短的临界区，不适合持锁执行长时间计算或等待磁盘、网络。

### 4.1 为什么“先检查，再设置”不够？

假设 `lock = 0` 表示空闲，`lock = 1` 表示占用：

```c
/* 错误示意：检查和设置不是一个原子操作 */
if (lock == 0) {
    lock = 1;
    /* 认为自己拿到了锁 */
}
```

两个执行者可能同时看到 `lock == 0`，然后都设置为 1，都认为自己拿到了锁。

因此，真正抢锁时需要原子操作，保证多个竞争者不能同时成功。

## 5. 原子操作是什么？

原子操作可以先理解为：**对其他并发执行者来说，这次操作是一个不可分割的单位。**

它和数据库事务有相似之处，但范围通常更小。数据库事务可以把多条数据库操作组织在一起；一次原子操作通常针对一个原子对象，不自动提供事务的回滚、持久化等能力。

```c
atomic_fetch_add(&a, 1);
atomic_fetch_add(&b, 1);
```

这是两次原子操作，不是一个同时更新 `a` 和 `b` 的事务。其他执行者可能在中间看到 `a` 已更新、`b` 尚未更新。

C 代码中的原子操作通常由编译器内置能力或原子接口表达，再由编译器生成目标 CPU 支持的机器指令或指令序列。原子性最终依赖平台提供的机制，并不是普通的几条 C 赋值语句自动具备原子性。

### 5.1 原子加减

```c
atomic_fetch_add(&count, 1);
atomic_fetch_sub(&count, 1);
```

原子加减把“读取旧值、计算、写回”作为一个原子操作，避免多个执行者的更新互相覆盖。

### 5.2 原子读取和原子写入

```c
#include <stdatomic.h>

atomic_int ready = 0;

atomic_store(&ready, 1);  /* 原子写 */
int value = atomic_load(&ready);  /* 原子读 */
```

原子读写的用途包括：

1. **完整读写**：读取不会得到由不同写入拼成的“半个旧值、半个新值”。
2. **并发访问规则**：在 C 多线程程序中，让编译器和 CPU 按原子操作规则处理对该原子对象的访问。
3. **同步**：结合合适的内存顺序，可以与其他操作建立可见性关系。

普通读写在很多情况下完全可以使用，例如变量只由一个线程访问，或者所有相关访问都受同一把锁保护。某些 CPU 对特定大小、正确对齐的数据，本身也能保证单次普通读写完整；但这不自动让 C 程序中没有同步的并发读写变成安全操作。

原子读写不一定需要执行加锁指令，也不保证读取一定立即得到另一个核心刚写入的最新值。具体机器指令取决于平台、类型和内存顺序。

**原子读加原子写，不等于原子加法：**

```c
int old = atomic_load(&count);
atomic_store(&count, old + 1);
```

两个执行者仍可能都读到同一个旧值，再各自写回相同的新值。应使用 `atomic_fetch_add()`，或者使用锁保护整个过程。

### 5.3 原子交换与 TAS

原子交换的含义是：写入新值，同时返回旧值，整个交换不可分割。

例如把锁变量原子交换为 1：

```text
旧值是 0：锁原来空闲，本次获取成功
旧值是 1：锁原来被占用，本次获取失败
```

TAS（Test And Set）常用于实现“尝试拿锁”。C 中可能通过编译器提供的原子交换接口实现。

### 5.4 CAS：比较并交换

CAS 是 Compare And Swap，意思是：只有当前值仍等于预期值，才把它改成新值。

```text
如果 lock 现在是 0，就原子地把它改成 1。
如果 lock 不是 0，报告失败。
```

比较并更新是一个整体。它可以用于抢锁、状态更新和一些更复杂的并发结构。

与原子交换相比，CAS 在预期值不匹配时不执行成功的更新。它在某些高竞争场景下可能更快，但效果取决于 CPU、指令实现、编译器和负载，需要测试；不能只凭 C 代码就断定。

### 5.5 原子位操作

一个整数的不同位可以表示不同标志。例如第 0 位表示“运行中”，第 1 位表示“需要停止”。

如果两个执行者通过普通的“读取、修改某一位、写回”同时修改不同位，仍可能互相覆盖。原子位操作把整个读改写作为一次操作：

```c
atomic_fetch_or(&flags, 1u << 0);  /* 设置第 0 位 */
atomic_fetch_or(&flags, 1u << 1);  /* 设置第 1 位 */
```

这与原子加法解决的是同一类问题：避免并发读改写时丢失更新。

## 6. 内存顺序：为什么看到标志还不够？

假设生产者准备数据，然后通知消费者：

```text
生产者：先写数据，再设置“准备好了”
消费者：看到“准备好了”，然后读取数据
```

我们希望消费者看到通知后，也能正确看到生产者之前写入的数据。这涉及**不同变量之间的同步关系**，不仅是某个变量本身读写是否完整。

C11 的一个示意：

```c
#include <stdatomic.h>

int data = 0;
atomic_int ready = 0;

/* 生产者 */
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);

/* 消费者 */
if (atomic_load_explicit(&ready, memory_order_acquire) == 1) {
    /* 如果读取到生产者发布的 1，可以读取已发布的数据 */
    printf("%d\n", data);
}
```

这里假设生产者发布后不再与消费者并发修改 `data`。消费者的 `if` 只检查一次，不会等待；如果检查时仍是 0，就跳过。

初学时可以先这样理解：

- **release**：发布前面的操作。
- **acquire**：读取到对应的发布时，建立同步关系。
- **relaxed**：保证该原子操作本身的原子性，但单靠它不建立上述发布关系。

同样的场景也可以用同一把互斥锁保护共享数据。锁不仅协调谁能进入临界区，也提供必要的同步关系。

没有同步的普通变量跨线程并发读写在 C 中可能构成数据竞争，不能因为某次测试输出正确就认为程序一定可靠。`volatile` 本身也不能代替锁或原子同步。

## 7. 为什么自旋锁竞争会造成 CPU 升高？

假设很多 CPU 核心同时竞争一把锁：

```text
一个核心持有锁，正在更新数据
其他核心不断检查或尝试获取同一把锁
```

等待者仍在执行指令，因此会消耗 CPU。如果它们反复对同一个锁变量执行原子读写，多个核心还需要协调缓存中的共享数据，进一步增加开销。

CPU 升高只是可能的现象；实际问题也可能来自其他代码。应结合采样热点、吞吐、延迟和负载判断，不能仅根据 CPU 使用率断定是自旋锁。

### 7.1 先读取，再尝试原子获取

一种常见优化是：

```text
先读取锁状态
    ├─ 看起来仍被占用：继续等待
    └─ 看起来空闲：执行原子操作尝试获取
```

普通读取只是预检查，不表示已经拿到锁。即使多个执行者同时看到空闲，最终仍要通过原子操作决定谁获取成功。

这样做可能减少锁被占用期间无谓的原子读写，但不能消除锁竞争。

### 7.2 自旋延迟与退避

失败后可以在重试前加入短暂延迟；反复失败后，也可以让执行者短暂睡眠。延迟太少可能导致无效重试过多，延迟太多则可能增加锁释放后的等待时间，需要根据具体实现和负载评估。

ARM64 的某些实现使用 `ISB` 指令产生自旋延迟。执行指令期间仍在使用 CPU；这与进程睡眠不同。

## 8. ARM64、x86 和 LSE

ARM64 和 x86-64 是不同的 CPU 指令集架构。同一份 C 代码可以由编译器分别生成适合各自架构的机器指令。

**ARM 不等于国产 CPU。** 国内外都有基于 ARM 架构设计的处理器；国产 CPU 也可以采用其他指令集架构，例如 LoongArch。

ARM 和 x86 都可能发生自旋锁竞争。同一个负载在不同机器上表现不同，可能涉及核心数量、缓存与核心间互连、原子指令实现、编译方式和软件的等待策略。具体国产 ARM 机器出现 CPU 冲高，需要结合该机器和负载验证，不能只凭架构名称判断。

### 8.1 LSE 是什么？

LSE（Large System Extensions）是 ARM64 的一组扩展，其中包括用于原子操作的指令。对同一种原子操作，编译器可能根据目标平台采用不同实现，例如：

- 使用独占读取、条件写入以及必要的重试；
- 在支持且实际启用 LSE 时，使用相应的原子操作指令。

CPU 支持 LSE，不代表程序一定实际使用它；还需要检查系统暴露的能力和程序的编译结果。使用 LSE 或 CAS 是否更快，也必须在目标机器上测试。

Linux 上可以初步查看：

```bash
lscpu
grep -m1 '^Features' /proc/cpuinfo
```

ARM64 的 `Features` 如果包含 `atomics`，通常表示系统向用户态暴露了 LSE 原子指令支持；还需要进一步确认具体程序是否使用了它。

## 9. 死锁与普通等待

普通等待：事务 A 持有某个资源，事务 B 等待；如果 A 结束并释放资源，B 可能继续执行。

死锁：形成相互等待的环，例如：

```text
事务 A：持有资源 1，等待资源 2
事务 B：持有资源 2，等待资源 1
```

PostgreSQL 会检测适用锁管理机制中的死锁并中止一个事务以打破等待。应用可以通过统一获取资源的顺序、缩短事务等方式降低死锁概率。

待补充：在测试环境中，让两个事务按相反顺序更新两行，记录错误信息和事务回滚情况。

## 10. 观察与排查

常用观察入口包括 `pg_stat_activity` 和 `pg_locks`：

```sql
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE datname = current_database();
SELECT pid, locktype, mode, granted, relation::regclass, transactionid
FROM pg_locks
WHERE database = (SELECT oid FROM pg_database WHERE datname = current_database())
   OR database IS NULL;
```

`pg_locks` 不是所有内部同步和行锁状态的完整清单；高 CPU 自旋也未必直接表现为可见的锁等待事件。应结合 CPU 采样、吞吐量、延迟、并发量和机器配置分析。具体视图字段与等待事件可能随版本变化。

`pg_stat_statements` 会汇总 SQL 统计；大量并发请求更新同一统计条目时，相关内部同步可能发生竞争。是否是某次 CPU 升高的原因，需要实际采样和对照实验。
